## 一、本次變更總覽

### 1. 值班名冊獨立化(roster.json)
- 每站台獨立名冊檔:`data/<站台>/roster.json`(A3 = 64 人含保養組 8 人;KL / NK = 空名單)
- **名冊真實來源 = roster.json**:值班工程師名冊(人員與屬性)以該廠 roster.json 為準;月份檔只負責排班資料(days)
- 與 `users.json`(登入帳號)完全分離
- app.js 內寫死的 `ENGINEERS`、`MAINT_DEFAULT_PEOPLE`、`MAINT_SCHED_M6~M9` 等範本/明細**全數移除**

### 2. 值班納編規則(工號唯一性)
- 新增人員 → 後端 `roster_add` 先查 `users.json`:
  - 工號**已存在** → `409` 拒絕,不允許新增
  - 工號**不存在** → 同時寫入 該廠 `roster.json` + `users.json`(ENG 帳號、空密碼,即可登入)
- 三廠同一規則,站台由 `currentSite` 帶入,互不污染

### 3. 名冊編輯 / 移除同步
- 編輯姓名、班別、組別 → `roster_save` 同步回該廠 roster.json
- 移除人員(生效月份 = 本月或更早)→ **立即自 roster.json 移除**;歷史月份檔保留其排班紀錄
- 移除(生效月份在未來)→ roster.json 保留並帶 `inactiveFromYm` 標記,**時間到自動清除**
- 防「復活」:已生效移除者只進記憶體供歷史月份顯示,永不遷移回 roster.json
- 自我修復:roster.json 遺失/清空但月份檔有人 → 依現有名單自動重建

### 4. 做二休二自動排班引擎
- 規則(以 2026/6~8 公告資料逐日驗證):
  1. **做二休二**:上 2 天 → 休 2 天,4 天一循環,六組相位錯開
  2. 休日標籤照 **LEAVE → REST → HOLIDAY** 三循環(各組相位不同)
  3. **不允許連續 7 天上班**:「上班」= 預設實際出勤日(ON / LEAVE 加班日),REST / HOLIDAY 中斷連續;`checkSevenDayRule()` 硬性檢核
- 資料來源優先序:2026 年 6~8 月用公告行事曆 `CAL_2026`(含人工微調)→ 其餘月份(2026/9 起、任何年份)以 2026/6/1 為錨點**自動推算**
- **保養組改由 roster 班別 / 組別計算**(與一般人員同引擎),僅工作地點固定 `KE` 以視覺區別(由 roster 的 `isMaintenance` 旗標決定);寫死的保養組明細已移除
- 已生成 / 已編輯的格子**永不被覆蓋**;同月重複生成結果冪等
- 微調權限:LEADER 與 ADMIN(持站台編輯鎖)可調整,1.5 秒後自動存檔寫回月份檔
- 順帶修正:原版 2027 年會誤套 2026 行事曆的跨年 bug(查表加年份守門)

## 七、已知限制與注意事項(誠實告知)

1. **推算班表 ≠ 公告班表 100%**:公告每月每組可能有 0~1 天的人工對調(週日/週一 REST↔LEAVE),推算不出來;新公告發布後請 Leader / ADMIN 對照微調(已編輯格子不會被自動生成覆蓋)。
2. **保養組現在走一般引擎**:寫死的保養組 6~9 月明細已移除;已存檔的 6~9 月保養組班表在月份檔中**不受影響**,但若重置或在空白月份重新生成,保養組會得到與同組一般人員相同的做二休二班表(loc=KE),需要的話再手動調。
3. **移除人員不會刪登入帳號**:users.json 帳號保留(避免移除生效前無法登入);要清帳號請至「帳號權限管理」。
4. 認證仍為「只驗工號」(LDAP 呼叫停用中),維持你指定的現狀。
5. `requirements.txt` 未含 `ldap3`,但 `app.py` 頂層有 import;乾淨環境部署需先 `pip install ldap3` 或自行加入 requirements。
6. README.txt 尚未補充 roster.json 架構說明(可另行更新)。
7. PREVIEW_MODE(離線單機)下 roster 不可用,名冊為空。
